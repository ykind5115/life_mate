feat(goals): 补齐 Goal 管理端点与投影记忆，并接入 Life Review

## 背景：docs/04 缺少 Goal 端点
§13.10 明确要求「用户不可直接新建 type='goal' 的记忆（必须通过 Goal 实体）」，
而 docs/04 §50 的接口清单里**没有任何 Goal 端点**。
两条规矩合在一起 = 用户完全没有创建目标的途径，
而 PRD §7.4 的「我的记忆」把「目标」列为一类。
因此这组端点是**补齐文档遗漏**，不是新功能。

## 按「V1.0 做简单些」收敛的范围
用户已确认采用手工显式管理（方案 B）：不做抽取、不做子目标/里程碑。

新端点：
  GET    /goals            列表（未完成优先 + 优先级降序）
  GET    /goals/:id
  POST   /goals            同时生成投影记忆
  PATCH  /goals/:id        状态机软校验 + 必要时重建投影
  DELETE /goals/:id        默认软删除，?hard=true 物理删除
  POST   /goals/:id/restore

## 投影记忆（§13.10 的必须①②④）
goals 表不参与向量检索，因此每条 Goal 同步维护一条 memory(type='goal')，
来源指针是 goal_id + source_type='goal_projection'。
没有它，用户问「我在忙什么目标」时 Agent 答不出来。

投影记忆刻意不带槽位：目标之间不存在「同槽位取值矛盾」，
给它们同一个 goal.long_term 槽位会撞 uq_memories_current_slot，
第二个目标就建不出来了。已加测试锁住。

## C24：硬删除的顺序不可调换
投影记忆的来源指针是 goal_id，而 goal_projection 不在
chk_sources_has_origin 的豁免列表里。
若不先清来源行就删 Goal，外键 SET NULL 会让来源行失去所有指针
→ CHECK 违约 → 整个删除被回滚（审计 F-03 实测过）。
已按 §13.10 的四步顺序实现，并有回归测试。

## 状态机：软校验而不是硬拒绝
docs/03 §21.3 只列了五个状态，没有给转移表。本实现按以下依据推出，
并选择软校验（非法转移执行但返回 warnings）：
  · 「标记完成了又发现没完成」是真实场景，硬拒会逼用户删掉重建（丢历史）
  · 库层 CHECK 拦的是非法取值（数据完整性），
    「completed → active」是业务语义，两者性质不同
唯一收紧的一处：completed/cancelled 不能直接回 active（会让
completed_at 与 status 不自洽），返回的 warning 里告诉用户可以新建目标。

注意：这份转移规则需要产品确认，已在交付说明中标注。

## 顺带
- Life Review 现在真的纳入 goals（此前把它列为「未接入」）。
  按「创建时间 ≤ 区间终点 + 状态为 active/paused」筛：
  持续进行中的目标是这段时间的主线，属于回顾；
  已终结的目标属于「已经结束的事」，列进去会让回顾杂乱。
- 目标在材料里单独成段且标注「仍在进行中」——
  与记忆混在一起会让模型把「想学吉他」写成「学了吉他」。
