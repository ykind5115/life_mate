## 1. 根本矛盾：防幻觉 vs 自然

这是本次讨论的核心，值得单独说清楚。

```text
PRD §10.2 要求：不能把推测当成事实，不能编造用户的经历
        ↓
提示词实现成了：反复声明「我没检索到」「这是部分记忆」
        ↓
代价：用户看到的是一个在解释自己工作原理的机器，不是朋友
```

**关键洞察：诚实和自然并不冲突，只是我们选错了表达方式。**

```text
❌ 现在的说法（在讲机制）         ✅ 应该的说法（在做人）
「我翻了长期记忆，没检索到」      「你还没跟我说过这个」
「我这边搜索不到相关记录」        「我不记得你提过」
「这是系统检索到的部分记忆」      「你之前跟我说过…」
「如果你之前确实聊过，换个        （直接问，不解释为什么可能找不到）
  说法我可能就能找到」
```

有一处提示词**写错了事实**，必须改：

```text
现状第 43-44 行：「不要声称你「记住了」本次对话」
问题：本次会话的上下文它**确实看得到**（最近 20 条原文 + 摘要）。
      真正看不到的是「更早的、没被检索到的」长期记忆。
      这两件事被混为一谈，导致它对当前对话也不敢确认，
      表现为过度免责。
正解：会话内 = 它知道；跨会话的旧事 = 可能不完整。
      两者要分开说。
```

## 2. 逐条方案

### 方案 1：注入时间（解决反馈 1.2 + 5）

**这是最高优先级 —— 它同时修掉两个问题，且成本最低。**

分三处注入：

```text
① 当前时间（system prompt 里）
   「现在是 2026-09-26 20:18，星期六」

   注意：注入的是**服务端时间**，不是"我算出来的"。
   此前它说"我没有时钟，看不到当前是几点" —— 那是因为我们没给它。

② 历史消息的时间（带间隙标记，不是每条都堆时间）
   只在**间隔较长**处插一条系统消息，避免噪音：

     [系统] 上面是 3 天前的对话
     （以下是最近的消息）

   阈值建议：超过 6 小时才标记，且同一天内只标一次日期变化

③ 事实的生效时间（已经有了）
   已知信息段落里已带「（2026-09-15 起）」
```

**为什么不给每条消息都加时间戳：**

```text
「[09-24 09:15] 康康你好」这类前缀
  · 会明显变吵，而且它本来就不该模仿这种格式
  · 大部分相邻消息间隔只有几十秒，标了没有信息量
真正需要时间感的是「跨天」「隔几天」，所以只在间隙处标记。
```

**阈值怎么定 —— 用你的真实数据校准（2026-09-26 实测）：**

```text
你的第一个会话：42 条消息，跨度 2 天 11 小时（09-24 08:51 → 09-26 20:18）

21 个发言间隔的分布：
  · 20 个在 1 小时以内（同一段连续对话，不需要标记）
  ·  3 个超过 1 小时
  ·  1 个超过 6 小时
  ·  1 个超过 1 天 —— 就是 2 天 5 小时那次，你反馈的「隔了两天」

结论：阈值定 1 小时左右合适。
      定 6 小时会漏掉 1~6 小时那两段「隔了半天」的间隔；
      定 5 分钟又会把同一段连续对话切得太碎。
      建议 1 小时，且跨天时额外标出日期。
```

**顺带一个实测发现（影响前端显示）：**

```text
同一轮的 user 与 assistant 消息 created_at **完全相同**：
  sequence 2 (assistant) 的 created_at == sequence 1 (user) 的

原因：两条消息在同一个事务里写入，而 now() 在事务内是常量
      （conversation-store 的注释里记过这个特性）。

影响：
  · 显示到「日期」没问题
  · 但**不能**用它算「它思考了几秒」—— 那个信息现在没存
  · 也不需要改：同一轮的两条本来就属于同一时刻的对话
```

**待你确认：**

- 当前时间要精确到分钟还是只到日期？
  建议：会话内精确到分钟（它能回答"现在几点"），但**只在 system 里给一次**
- 界面上的消息要不要显示时间？
  建议要（前端现在也没显示）。用户自己也需要看到"这条是三天前说的"

### 方案 2：自动生成会话标题（解决反馈 4）

**方案选择 —— 这是本次讨论最需要你决定的一处：**

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A. 取首条消息截断** | 拿用户第一句话截前 20 字 | 零成本、瞬时、无 LLM 调用 | 「早上好呀，你知道现在是…」这种开头当标题很难看 |
| **B. 首轮后 LLM 生成** | 第 2 轮对话后调一次模型，给 5-10 字标题 | 标题质量好（「公安运维工作咨询」） | 多一次 LLM 调用；要处理失败降级 |
| **C. 先 A 后 B** | 立即用 A 占位，拿到 LLM 标题后替换 | 列表立刻可用，之后变好 | 实现稍复杂 |

**我倾向 C**，理由：

```text
· 列表的可用性不能等 —— 用户发完第一条就该看到它
· 但首条消息当长期标题确实差，尤其问候语开头
· 两者结合成本很低：A 是纯字符串操作，B 是复用已有的后台触发机制
  （与摘要/抽取同一套 fire-and-forget 模式，代码可以照抄）
```

**待你确认：**

- 选哪个方案？
- 标题用不用 LLM？如果用，模型给的标题可能带标点与引号，要不要清洗格式？

### 方案 3：重写系统提示词（解决反馈 1、3、6）

这一条是**改动最大、也最需要你参与判断**的，因为它是产品性格的定义。

我建议改五处：

#### 3.1 记忆表达：从「讲机制」改成「说人话」

```text
❌ 删掉：「你能看到的是系统检索出来的一部分长期记忆」
❌ 删掉：「直接说明你没找到，并建议用户换个说法或补充细节」
❌ 删掉：「以上是系统检索到的部分记忆，可能不完整」
❌ 删掉：「不要声称你记住了本次对话」

✅ 换成：
   - 你知道的是这段对话里说过的，加上之前留下的印象。
     更早的事可能想不起来 —— 想不起就说想不起，别说"检索不到"。
   - 永远不要描述你是怎么工作的：不说"记忆""检索""上下文""系统"。
     想不起来时用人的说法：「你还没跟我说过」「我记不清了」。
```

**关键：把"可以想不起来"保留，把"解释为什么想不起来"去掉。**
防幻觉的要求不受影响 —— 它仍然不会编，只是不再解说机制。

#### 3.2 提问数量：加硬性上限

```text
✅ 新增：
   - 一次最多问一个问题。想问的事多，挑最想知道的那个先问。
   - 不要连珠炮。宁可分几轮聊，也不要一次问三个。
```

反馈 3 的那个例子一次问了 3 个 —— 现在的提示词完全没提过数量，它自然不知道。

#### 3.3 该引导才引导

```text
✅ 新增：
   - 提问是为了更懂对方，不是为了把对话填满。
   - 对方只想聊两句、或情绪不高时，不要追问。
   - 同一个话题不要反复深挖。对方已经说清楚的事，不要再问一遍确认。
```

反馈 3 说的「不该引导的时候不要没话找话」在这里落地。

#### 3.4 话题切换要接住，不要总结与追问

反馈 6 那个例子的问题：

```text
用户：我不想聊这个话题了
它：  「好，那就不聊。你这几天假期主要是睡觉，聊了工作、聊了她，
       也说了学 agent 的进度。还有一天假，明天想干嘛，随你。」

问题出在：
  · 做了一次「对话内容总结」—— 像会议纪要，不像朋友
  · 「随你」是敷衍收尾
  · 换话题时又抛了一个问题
```

```text
✅ 新增：
   - 对方说不想聊某个话题时，就停下。
     不要总结已聊过的内容，不要追问，也不要说"随你"这类敷衍收尾。
     直接接住对方接下来想说的。
```

#### 3.5 整体语气：从"助手"改成"熟人"

```text
✅ 新增：
   - 说话像一个认识了一段时间的朋友：自然、口语、有自己的判断。
   - 可以有自己的看法，不必每句都附和。
   - 不要用客服口吻（"有什么可以帮您""希望对您有帮助"）。
   - 不要在每句结尾都附一个问句。
```

**⚠️ 这一条需要你参与：**

```text
现在的提示词刻意写了「不写鼓励性的人格设定 ——
PRD 要求的是陪伴与整理，不是拟人化扮演」。

你这次反馈的诉求，本质上是想要**更多人格**。
这两者是冲突的，需要你定一个度：

  · 到什么程度算"像朋友"，什么程度算"过头了"？
  · 要不要给它一个名字之外的身份背景（年龄、说话习惯）？
  · 要不要允许它偶尔表达自己的偏好（「我个人觉得…」）？
```

### 方案 4：记忆确认机制（反馈 2）—— 建议不改

你的判断我同意，**而且现有实现的行为正是你期望的**：

```text
你说的原则：「不确定的信息和我确认之后才写记忆；
              但我没确认时，默认模型是对的；
              只有我明确说不对才改」

现有实现：
  · 抽取流水线立刻写入（不阻塞对话）→ 对应「默认模型是对的」
  · 模型在回答里询问确认         → 对应「和我确认」
  · 你纠正后，下一轮抽取会把新信息作为新事实写入、
    旧记录走 supersede 或 conflict → 对应「明确说不对才改」

所以这条**行为已经符合你的期望**，不需要改代码。
```

**可以改进的是「更正的成本」**，两点：

```text
① 你纠正之后，旧的那条错误记忆会怎样？
   取决于槽位：
     · 有槽位的（employment.role 这类）→ 自动 supersede，旧的标记为已替代
     · 无槽位的 → **不会自动失效**，会与新记忆并存

   已核实代码（candidate-processor 分支一，第 163-166 行）：
     if (slot.predicateKey === null || slot.objectValue === null) {
       const memory = await createMemory(createInput, ...);   // 直接新增
       return { kind: 'created', memory, reason: 'no_slot' };
     }
   无槽位记忆**不参与冲突判定**，所以永远走「新增」分支。

   你那个例子里的「互联网主场技术工程师」正是无槽位记忆
   （模型没给它 predicate_key），因此你的更正不会让它失效 ——
   需要你手动去「记忆」页删。这是 C28 的已知取舍
   （无槽位记忆不受唯一约束），但对你来说是实际负担。

② 可以在记忆页加一个「这条不对」的快捷操作吗？
   比现在的「删除」更明确 —— 它应当同时记录「用户否定了这条」，
   让抽取器下次不要再从同一段对话里抽出它。
```

**这一条指向一个更根本的问题，值得单独讨论：**

```text
「无槽位记忆不参与冲突判定」这个设计的前提是
「词表之外的信息不参与判定，只存储」（§13.7）。

但真实使用中，**大部分记忆都是无槽位的** ——
你的数据里 11 条记忆只有 5 条有槽位。
那么「用户更正了错误信息」这条最常见的需求，
恰好落在**唯一没有被处理的那条路径**上。

三个可能的方向：
  A. 给无槽位记忆也做去重/失效（需要语义判重，成本高且不可靠）
  B. 记忆页加「这条不对」手动操作（成本低，但要你动手）
  C. 抽取器在「用户明确更正」的场景下，主动把旧记忆标为 superseded
     （需要模型能识别「他在纠正我」，且要能定位是哪条）
我倾向 **B 先做，C 作为后续**：B 立刻可用且确定，C 依赖模型判断，需要先验证。
```

**待你确认：** ② 要不要做？方向 A/B/C 选哪个？

## 3. 建议的实施顺序

```text
第一批（修 bug + 低风险高收益）
  ① 注入时间              ← 同时解决反馈 1.2 与 5，改动集中在 context-builder
  ② 会话标题（先做 A 占位） ← 列表立刻可用
  ③ 前端显示消息时间       ← 你也要能看到"这条是三天前说的"

第二批（提示词重写，需要你参与定调）
  ④ 记忆表达改成说人话     ← 反馈 1
  ⑤ 提问数量上限           ← 反馈 3
  ⑥ 话题切换不总结不追问   ← 反馈 6
  ⑦ 整体语气               ← 需要你先定「人格到什么程度」

第三批（按需）
  ⑧ 标题用 LLM 生成        ← 依赖 ②
  ⑨ 记忆页「这条不对」      ← 需要你确认是否要
```

**为什么把提示词放第二批**：它是产品性格的定义，改动会牵动所有回答。
而你刚才提到的那些例子很有价值 —— 我建议**改之前先按第一批做**，
把那几个例子在改后重跑一遍对比，这样能看清「哪些是提示词的问题、
哪些是缺少时间信息导致的」。否则两个变量一起动，说不清哪个起了作用。
