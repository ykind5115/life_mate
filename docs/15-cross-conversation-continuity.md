# 跨会话衔接缺失 — 问题分析与方案

**日期：** 2026-10-08
**来源：** 用户实测反馈 —— 短时间内开两个对话，第二个对话接不上第一个
**状态：** ✅ **已实施** —— 但有重要保留，见 §7

---

## 0. 结论

用户的判断是对的，但成因比「闲聊没被总结成记忆」更直接：

> **上下文组装只看当前会话。新会话第一轮的历史是空数组。**

`chat-service.ts` 取历史消息时按 `conversationId` 过滤
（`findRecentMessages({ conversationId })`），因此**跨会话的对话原文从来不会进入上下文**。
记忆检索虽然能跨会话，但它给的是「长期事实」，不是「刚刚聊到哪」。

所以这不是记忆质量的问题，是**少了一层上下文**。

| 时间窗 | **2 小时** |
| 注入条数 | **6 条** |

不是产品选项。单用户下「某段对话不想被延续」才是个产品开关，用户没有这个需求。

## 7. 实施结果与保留（2026-10-08）

### 7.1 做了什么

```text
① src/database/repository/conversation-store.ts
   findPreviousConversationWithTail()
   · 按 messages 的 max(created_at) 找「最后说话最新」的会话
     （不用 conversations.updated_at —— 它会被标题生成等后台动作刷新，
       与「用户最后说话的时间」不是一回事）
   · 必带 user_id 过滤（多用户隔离的唯一依据）
   · 排除已删除会话、排除自己、只按时间窗
   · 末尾 N 条按时间正序返回

② src/conversation/context-builder.ts
   · buildPreviousConversationSection()：明确的来源标注段落
   · 位置在摘要之后、当前会话历史之前
   · 只在调用方传入时出现（会话轮次的判断在调用方，本模块不查库）
   · meta.previousConversationCount 只记条数，不记内容

③ src/conversation/chat-service.ts
   · 只在 history.length === 0 时取（新会话第一轮）
   · 查询失败降级为「没有上一个会话」，绝不让对话失败

④ src/conversation/prompts.ts（关键补充，见 §7.3）
   「关于记忆」补两条：记得的事正常说 / 别把知道的说成不知道
```

### 7.2 实测：好了一次，但也坏过

用用户真实的两个会话重放（会话 A 的末尾 6 条 + 会话 B 的开场白与追问），
跑了 5 次，**结果从"完整承认"到"彻底否认"都有**：

```text
一次：✅「记得啊，问卷生成和改动那块——先跑通对话生成，再改问卷，
        初版差不多了，接下来是前端页面加连模型 API。」
      ← 完整、准确，正是期望的延续

一次：⚪「这个我记不清了，你之前提过问卷系统这事儿，但具体是什么
        我这边没太存住」← 承认部分，语气打折

三次：❌「问卷系统这个我还真没听你讲过，你刚才只说了『做项目』」
        「这个我还是第一次听你说，之前没聊过吧？」
      ← 与改之前完全相同的故障
```

**所以：机制修好了，行为没稳定修好。**

### 7.3 定位到的真正原因

用探针把 `buildChatContext` 的输出原样打印、再直接问模型
「你上面能看到什么」，模型回答：

> 能看到。有一段是前面聊的，里面有问卷和项目的事。原样引一句：
> 「等我把初版弄完之后，看看能不能正常对话生成和改动问卷」

**结论分两层：**

```text
✅ 上下文组装完全正确 —— 注入存在、位置对、模型读得到、能逐字引用
❌ 自然对话里它不用这些信息，反而会否认
```

于是问题不在注入，在**系统提示词的「关于记忆」章节**。原文是：

```text
你会记得对方以前说过的事……可能不完整 —— 有些记得，有些想不起来
想不起来的时候，就用平常的说法：「你还没跟我说过这个」「这个我记不清了」
不要对记忆里没有的事下断言。
绝不允许编造对方的经历、偏好或计划。
```

**整节只写了「怎么承认不知道」，没有一句允许它把知道的事说出来。**
模型对「断言」过度谨慎，于是在两个选项之间稳定地选了否认。
更糟的是它会**为一个错误的否认编造依据**（「你刚才只说了『做项目』」）——
而注入的上下文里明明写着问卷相关的话。

补的两条就是针对这个：

```text
**记得的就正常说，别先自我怀疑。** 上面列出的事、以及对话里出现过的事，
都是你知道的 —— 直接接着聊，不要一边说一边打折扣。

**但别把知道的说成不知道。** 说「你没说过」之前先确认一遍 ——
上面列出的事、对话里说过的事，都不能说没听过。对方说「我刚才讲过」时，
先回头看，而不是先否认。明明在眼前却说没听过，比记错更伤人。
```

注入段落里也加了一句显式消歧（这条最关键）：

```text
🔴 这一条最重要，它和系统规则里「想不起来就说『你还没跟我说过』」并不冲突：
   那条规则适用于**你想不起来的记忆**。而上面这些内容此时此刻就在你眼前，
   不是「想不起来」……
```

不加这句时，模型会把「另一个对话的内容」归类成「我想不起来的记忆」，
然后按那条规则否认 —— 这解释了三跑里两次否认。

### 7.4 实施中犯的两个错（都必须记）

🔴 **`excludeConversationId: existingConversationId ?? ''` —— 功能 100% 失效**

```text
空串被拿去和 uuid 列比较，PostgreSQL 报
  invalid input syntax for type uuid: ""   （22P02）
而这个查询恰好只在新会话第一轮跑 —— 也就是 existingConversationId
为 null 的那一次。所以它在**真实场景下从不生效**。

为什么测试没抓到：我写的 9 个仓储测试全都传了合法 UUID。
**测试覆盖的是「方便测试传的形状」，不是「调用方真正会传的形状」。**
可选参数必须测「不传」—— 现已补上这两条用例。
```

🔴 **server.test.ts 的顺序依赖：只在全量跑时失败**

```text
那个夹具从不清理会话，会话在测试库里累积。
跨会话衔接会把「2 小时内最后说话的那个会话」注入新会话，
于是断言「上下文只有 system + user」的用例开始失败 ——
而且单跑该文件时恰好不满足条件，只有全量跑才炸。

这暴露的是测试夹具的隔离缺陷，不是功能缺陷。
已修：夹具开头清掉当前测试用户名下的会话。
（AGENTS.md §4.5 记过同类坑的两种形态，这是第三种。）
```

### 7.5 仍未解决 / 下一步建议

```text
🔴 模型仍可能否认它看得见的内容（5 次里 3 次）
   这是**元认知问题**，不是上下文问题：
   模型对「我知道什么」的判断不可靠，且在规则压力下倾向保守否认。
   本轮把提示词的缺口补上了，但 5 次样本太少，不足以断言已解决。

   建议：先用一段时间观察真实使用。若仍频繁出现，可考虑的方向：
     · 把上一个会话的内容作为**真实对话轮次**注入，而不是 system 块
       （对照实验做了一次：那一次模型完整承认了，但样本=1，不足以下结论；
         且它破坏了「当前会话」与「上一会话」的边界，代价需要评估）
     · 会话内第一条消息就注入（而不是等用户提起）

🟠 时间窗是「最后一条消息」距现在 2 小时
   若用户先开了新会话、晾了 3 小时才说话，则接不上。
   这个边界符合「2 小时」的字面意思，但可能不符直觉。观察后再定。
```

## 2. 为什么现在接不上

### 2.1 三层上下文里没有「上一个会话」这一层

`docs/10 §3.2` 记录的现有层次：

```text
┌─ 系统规则
├─ 长期记忆（本次相关的最多 8 条，带生效日期）
├─ 更早对话的摘要（仅当**本会话**很长时才出现）
├─ 当前会话最近 20 条消息的原文        ← 只覆盖当前会话
└─ 你刚说的这句
```

```text
❌ 没有「刚刚在另一个会话里聊了什么」
```

### 2.2 摘要也救不了 —— 它是按会话存的

`listActiveSummaries(existingConversationId)` 同样按会话过滤，
且 B 是刚开的会话，没有任何摘要。

### 2.3 记忆检索能跨会话，但答的是另一个问题

本次实际注入的记忆里**确实有问卷系统**：

```text
「用户接到一个 AI 工作流程项目，目标是用模型完成问卷系统的全流程：
  问卷设计、下发、审核、人工回填以及回填后的审核」  ← 命中了
```

模型在 seq8 也把它复述出来了。**但这条记忆是"国庆前的状态"**，
不含 10:09–10:14 那几轮的关键结论：

```text
· 决定「把当前状态喂进去、让模型基于状态改」而不是重放对话历史
· 决定在结构旁挂一个「约束字段」记面向将来的规则
· 初版已差不多，下一步做前端页面 + 连模型 API，当晚测
```

于是出现最讽刺的一幕：**它记得住"用户在做问卷系统"这个月级事实，
却记不住"一分钟前刚聊过问卷系统"。**

用户的原话点出了要害：

> 不是所有的事情都会被总结，形成记忆，但是短时间内的闲聊还是需要作为
> 上下文的一个部分的，毕竟是"好伙伴"，闲聊也是占很大比重的。

## 3. 方案

### 3.1 核心做法：注入「上一个会话的尾巴」

新会话开始时，若上一个会话**刚刚结束**，把它的末尾若干条原文
作为一段**明确标注来源**的上下文注入。

```text
┌─ 系统规则
├─ 长期记忆（不变）
├─ 更早对话的摘要（不变）
├─ 【新增】刚刚在另一个对话里聊到  ← 标注来源与时间
├─ 当前会话最近 20 条消息的原文
└─ 你刚说的这句
```

**位置必须在当前会话历史之前**，理由与 §12.4 对摘要的要求相同：
它讲的是「之前」的事，放在后面会被模型当成刚发生的。

### 3.2 触发条件（三个都要满足）

```text
① 上一个会话的最后一条消息距现在 ≤ 时间窗（建议 2 小时，可配置）
② 当前会话刚开（历史消息数为 0）—— 只在第一轮注入，之后不再需要
③ 上一个会话存在且有消息
```

**为什么必须限定「当前会话是新的」**：
会话进行到第 5 轮时，当前会话自己的历史已经足够，
再塞上一个会话只会白占 token、还可能把话题带偏。

### 3.3 注入的形状

```text
【刚刚在另一个对话里聊到】（10:09 – 10:14，距今 1 分钟）

  你：作为日志，因为这个系统核心还是问卷，模型获取上下文不重要，
      直接把要修改的问卷模板结构放到上下文中比放对话记录效率高的多……
  我：方向我同意……这里有个缝值得补一下：有些约束只存在于对话里，还没落进结构。
      所以我会在结构旁边挂一个很小的约束字段……
  你：有道理，等我把初版弄完之后，看看能不能正常对话生成和改动问卷……
  你：现在初版已经差不多了，把前端页面设计一下，连上模型的API就可以测试了……

⚠️ 这是**另一个对话**里的内容，不是当前这段对话。
   若对方提到「刚才说的」，优先理解为上面这些。
   不要说你没听过 —— 你见过，只是来自另一个对话。
   若确实不在这里，直说「这部分我这边没有」，不要编理由。
```

**三点设计意图：**

```text
· 明确标注「另一个对话」→ 它才能诚实地说「你在另一个对话里提过」，
  而不是被自己的上下文搞糊涂（现在的问题是它连自己看过什么都不知道）
· 最后两条约束是直接针对本次的 ②③：
   不要编「你没细讲」这类理由
· 条数上限（建议 6 条）+ 时间窗，保证 bounded
```

### 3.4 参数建议

| 参数 | 建议值 | 依据 |
| --- | --- | --- |
| 时间窗 | **2 小时** | 与 `TIME_GAP_MARKER_MINUTES = 60` 的口径一致：超过这个量级就不是「同一段连续对话」了。2 小时是「连着聊」的宽松上界 |
| 条数 | **末尾 6 条** | 3 轮往复。足够覆盖「刚才在聊什么」，又不会喧宾夺主 |
| token 预算 | **单独 ≤ 800** | 记忆已有 2000 的预算，这一层不该同等份量。超出就从头截断 |

### 3.5 与「时间标记」的关系（已经有的机制）

`context-builder` 已有 `buildTimeMarker`（间隔 ≥ 60 分钟才打标记）。
本方案与它是**互补**的：

```text
时间标记   解决「同一个会话里隔了很久」 → 让模型知道「上次是两天前」
上一会话   解决「换了个会话但时间连着」 → 让模型知道「刚才在隔壁聊过」
```

两者合起来才是完整的时间感：**现在既能感知"隔得久"，
也能感知"换了窗口但没隔多久"。**

## 5. 「跨会话可见」的边界（已澄清）

本文初稿把「跨会话可见」写成一个需要用户决定的产品开关，**那是表述错误**，
用户也直接指出了：

> 跨会话可见不能设置用户过滤条件吗？假如说多用户的话，
> 用户隔离应该能避免把别人的对话加载到另一个人的上下文中吧

对的。这里有两件不同的事，初稿把它们混为一谈了：

```text
① 多用户隔离  → **不是产品选项，是查询条件**
   与记忆检索同一个纪律：一切查询必带 user_id。
   少写它 = 把别人的对话拼进当前用户的上下文（隐私事故），
   而且静默发生。已实现并有专门的红线测试守着。

② 单用户下「某段对话不想被延续」→ 这**才是**产品开关
   用户没有这个需求，因此不做。
```

## 6. 顺带发现的另一个问题（独立于本方案）

本次对话暴露的 ②③ —— **编造「我没听过」的理由** —— 与 09-29 那次幻觉同源：
模型对自己「知道什么」没有可靠感知。本次方案能消除这一个具体场景
