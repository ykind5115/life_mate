# 移动端适配（手机竖屏）

**日期：** 2026-10-13
**来源：** 用户实测反馈 ——
> 「这个应用是部署在本机的，但是呢，我用 Tailscale 在手机上也能访问。
>   但是有个问题可能要大改前端：我在手机上的浏览器访问这个应用的时候，
>   前端格式乱得很，非常不适合手机竖屏访问。」

**状态：** ✅ 已实施（§5 是实施记录）

---

## 0. 结论先行

```text
① 这不是框架问题，也不是「要写安卓端」的问题 —— 是**响应式没做**。
   viewport meta 有、媒体查询也有两条，只是那两条写得很薄（见 §1）。
② 换 React / Vue / Next.js 不解决任何问题：它们只渲染 DOM，
   布局还是同一套 CSS，同样的断点错误会一模一样地重现，
   还多一个构建步骤（现在是零构建）。
③ 安卓原生 App 对「一个人的工具」不划算：两个前端要同步维护，
   以后每加一个功能做两遍；而且 API 走 Tailscale，
   App 还得认这个地址。V1.0 不该走这条路。
④ 正确做法：保留一套代码，手机上**换一种交互形态**
   （底部标签栏 + 对话页单栏），而不是把桌面版缩小。
```

用户决定（§4 问过）：

```text
· 手机端定位：**聊天为主**（先把对话页做到好用，其余页面「能用」即可）
· 导航形态：**换成底部标签栏**（而不是把桌面版缩小）
```

## 1. 「格式乱」的三个实测原因

不是猜的，是读 `public/app.css` 与 `public/index.html` 得出的。

```text
① 侧栏在手机上吃掉一半以上高度

   .sidebar { width: var(--sidebar-w) }   ← 900px 断点把它从 216px 缩到 64px
   .nav     { flex-direction: column }    ← 但排列方向还是竖的
   8 个导航项 × 约 44px = 352px，加 brand 与 health
   手机竖屏可视高约 700px → 侧栏占掉一半以上
   剩下的是「8 个孤零零的图标竖着排一长条」

② 打开对话，第一眼看到的是会话列表，不是消息

   640px 断点里 .chat-layout { flex-direction: column }
   → 左栏「历史会话」(限高 168px) 排到了消息**上面**
   → 每进一次对话都要先滚过它

③ 输入框 / 轨迹面板 / 图谱在 640px 断点里一处都没覆盖

   .composer   全文 12 处规则，640px 内 0 处
   .trace      全文 13 处，      640px 内 0 处
   .graph      全文  7 处，      640px 内 0 处
```

另外两个隐形的坑（看不出来但很难受）：

```text
· iOS Safari 在 font-size < 16px 的输入框上会自动放大整页 ——
  用户一打字页面就缩放。必须给输入框 16px。
· 手机地址栏收起时 100vh 会算错（比可视高度大），
  底部内容被顶出屏幕。要用 100dvh。
```

## 2. 方案：一套代码，两种形态

```text
桌面（> 900px）        平板（640–900px）      手机（< 640px）
──────────────────────────────────────────────────────────────
左侧栏 216px           图标条 64px            **底部标签栏 56px**
  ├ 品牌名               └ 只有图标              ├ 横排 8 项，4 个一屏
  ├ 8 项带文字                                   ├ 图标 + 小字
  └ 健康状态                                     └ 可横滑

对话页：两栏并排        对话页：两栏并排        对话页：**一次一栏**
  ├ 历史会话 260px        ├ 200px                ├ 「历史会话」与「消息」互斥
  └ 消息 + 右侧记忆栏     └ 消息                  ├ 标题栏 ☰ 切换
                                                 └ 右侧记忆栏 → 抽屉（🧠）
```

关键点：**手机上不是把两栏挤在一起，而是一次只显示一栏。**

实现方式是 `.chat-layout` 上的一个类：

```text
.chat-layout.is-mobile-list  →  显示会话列表，隐藏消息
.chat-layout:not(...)        →  显示消息，隐藏会话列表

⚠️ 这两条规则**只写在 @media (max-width: 640px) 里**。
   桌面下这个类一直存在但没有视觉效果 ——
   于是 JS 不需要判断屏幕宽度，逻辑简单很多。
   有一条测试专门守住这个约定（见 §5）。
```

## 3. 为什么不用 `calc(100dvh - 56px)`

一个差点写错的地方，值得记下来：

```text
.shell 是 display: flex; height: 100dvh，.sidebar 是 flex: 0 0 56px，
.main 是 flex: 1。

所以 .main 的高度**自动**就是 100dvh - 56px。
如果给 .main 再写 calc(100dvh - var(--tabbar-h))，
就是**减了两次** —— 内容区凭空少 56px，
表现为底部留一块空白，而且很难想到是这里。
```

## 4. 用户决定的问题

```text
① 手机端定位？
   → 「聊天为主（先把对话页做到好用）」
     因此：对话页做深度适配；其余页面只保证「不溢出、能滚动」。

② 导航换成底部标签栏？
   → 「可以，底部标签栏更像手机 App」
     因此：侧栏在 640px 以下改横排、贴底，腾出的高度全给内容。

③ 知识图谱在手机上怎么办？（我问过，用户没明确回答）
   力导向图 + 拖拽缩放在触屏上天生难用，这是所有图可视化在移动端的通病。
   本轮的做法：给它一个最小高度（55dvh）保证能看见、能滚，
   **不追求好用** —— 与「聊天为主」的定位一致。
   将来若要认真做，方向是「手机上换成列表/树形展示，而不是力导向图」。
```

### 🔴 顺带发现一个测试基础设施的缺陷

```text
桩的 fetch 用带方法前缀的 key 查表：
    const key = `${init?.method ?? 'GET'} ${url.replace('/api/v1', '')}`
即 'GET /conversations/c1'。

而**现有用例一处都没有按这个格式传 routes** —— 全都没命中过，
拿到的都是 data: {}。

它之所以一直没暴露，是因为现有用例大多只断言「不抛错」「渲染出提示」，
空数据也满足那些断言。我是因为新用例断言了**会话标题**
（必须有真数据才可能通过）才发现。

修法：
  · 新用例的 routes key 统一加 'GET ' 前缀
  · bootApp 的注释里写明这个格式要求，并说明这个坑
  · 加 DSH_DOM_DEBUG=1 开关：跑测试时打印每个请求「命中= true/false」。
    写需要真数据的新用例时先打开它确认 —— **命中失败默认是无声的**，
    它会伪装成「功能没实现」，很费时间。
```
