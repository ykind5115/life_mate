# 第一部分：怎么用

## 1. 启动

需要两个终端窗口。

**窗口一：启动依赖服务（开机后跑一次即可，可一直开着）**

```powershell
cd D:\workspace\LifeMate
docker compose up -d
```

**窗口二：启动应用**

```powershell
cd D:\workspace\LifeMate
pnpm dev
```

然后浏览器打开：

```text
http://127.0.0.1:2003
```

**停止**：窗口二按 `Ctrl+C`。依赖服务可以不管（占用很小），要停就 `docker compose stop`。

## 2. 界面有六个页面

| 页面 | 用途 | 要点 |
| ---- | ---- | ---- |
| **对话** | 日常聊天 | 逐字输出。每条回复下方显示「召回 N 条记忆 · 调用 N 次工具」——你能看到它想起了什么 |
| **记忆** | 看它记住了什么 | 支持语义搜索（不是字面匹配，问「我平时喝什么」也能找到「喜欢手冲咖啡」）。可删除、可恢复 |
| **时间线** | 人生事件 | 换工作、搬家这类有明确时间点的事，按年月排列 |
| **目标** | 长期目标 | **需要手动添加**，不会自动抽取（理由见下方 §3.3） |
| **回顾** | 生活回顾 | 选「这一周 / 这个月 / 今天」，生成一段叙述 |
| **设置** | 配置 | `auto_extract` 开关：关掉后不再自动整理记忆，已有内容不受影响 |

侧栏底部显示服务状态，侧栏上方显示「已记住 N 条」。

## 3. 使用上的几件须知

### 3.1 记忆是**跨会话**的

点「新会话」只是换一段对话，记忆不会重置。它记得的仍然记得——这正是这个项目的目的。

### 3.2 三层上下文：会话内 / 摘要 / 长期记忆

这是最容易误解的一点，先说结论：

> **同一个会话内的上下文是完整的，与「抽取要 4 条消息才触发」没有任何关系。**

抽取管的是**跨会话的长期记忆**，不是当前对话能不能接上。两者是独立的两层。

一次回答实际看到的东西，从上到下：

```text
┌─ 系统规则（角色、行为约束）
├─ 长期记忆（本次相关的最多 8 条，带生效日期）
├─ 更早对话的摘要（仅当会话很长时才出现）
├─ 当前会话最近 20 条消息的**原文**
└─ 你刚说的这句
```

所以下面这种连续性**天然就成立**，不需要等后台抽取：

```text
你：我最近在玩《博德之门 3》，喜欢这种能自己做选择的 RPG。
它：（回应）…
你：那你觉得这个游戏里哪个角色最好？        ← 「这个游戏」能正确解析
它：（回应，并知道说的是博德之门 3）
你：它的剧情跟《神界原罪》比怎么样？        ← 「它」继续指代
```

**已实测验证**（2026-09-24，真实模型 4 轮连续对话）：

```text
轮次   历史条数   注入记忆   结果
 1        0          0      正常回应
 2        2          0      正确理解「这个游戏」= 博德之门 3
 3        4          0      正确理解「它」
 4        6          0      准确复述，并主动区分「你在玩的」与「你拿来对比的」
```

关键在第 2、3 轮的**注入记忆 = 0**（抽取还没触发过），它照样接得上——
证明连续性来自会话上下文，不是抽取。

### 3.2.1 那 4 条阈值到底影响什么

```text
❌ 不影响：当前会话能不能接上话       （那是最近 20 条原文的职责）
✅ 影响：  关掉这个会话、过几天再聊时它还记不记得
```

举例：

```text
场景 A（同一会话内，连续说）
  你：我在玩博德之门 3
  你：这个游戏哪个角色最好？          → 一定接得上（在最近 20 条里）

场景 B（关掉会话，第二天新会话）
  你：我上次说的那个游戏，哪个角色最好？ → 需要长期记忆已抽取出来
                                         （此时"游戏名"是否被记住取决于抽取质量）
```

所以如果只是**担心连续对话会断**，不用担心。真正可能失手的是场景 B——
而那属于抽取质量问题（见 §7.2 的已知问题）。

### 3.2.2 会话很长之后会怎样

最近 20 条是原文。超过之后，更早的部分会被**压缩成摘要**继续带着：

```text
消息累计 > 30 条 → 对最早的 20 条生成一段摘要
摘要放在最近消息之前（时间顺序不能反，否则模型会误判先后）
```

摘要是有损的，因此注入时明确标注了「有损压缩，细节可能不准，
不确定就说不知道，不要凭摘要推断」。

**代价**：几百条消息之后，很早的细节会变模糊。这是刻意的取舍——
另一个选择是无限把历史塞进上下文，那既贵又慢，而且到某个点必然超限。

### 3.3 记忆不是实时的

后台抽取需要几秒到几十秒（取决于模型速度与消息量）。默认累计约 4 条消息才会触发一次整理。所以：

- 刚说完一句重要的话，**不要立刻去「记忆」页确认**，等十几秒
- 没看到不代表没记住，可能是还没轮到

（注意：这只影响「去记忆页看」与「跨会话回忆」，不影响当前对话。）

### 3.4 目标为什么是手动的

按你的决定（V1.0 做简单些）实现为**手工管理**。理由是目标有生命周期（进行中/搁置/完成/放弃），让用户显式管理比让模型猜可靠。

对话里提到的目标信息仍会被记住（作为 `goal.long_term` 槽位的记忆），只是不会自动变成「目标」条目。

### 3.5 它对不确定的信息会保留冲突而不是硬改

如果你说的新信息与已有记忆冲突（例如先说住南京、后说搬到杭州），系统可能：

- 把旧的标记为「已替代」，写入新的（信息明确变化时）
- 或把新的标为**待裁决**，等你在「记忆」页看到它

它**不会**悄悄把旧记录改掉——Q1 决策要求记忆正文不可变，历史要保留。

### 3.6 有些设计是刻意的

| 现象 | 为什么 |
| ---- | ---- |
| 它说「我这边没有记录」而不是「你没提过」 | 检索不到 ≠ 用户没说过。提示词明确要求它区分这两件事 |
| 它偶尔反问「是我记错了吗」 | 发现记忆与你说的不一致时的正确行为 |
| 它不做心理分析 | PRD §10.3 明确要求 |
| 回答里有「这是你之前提到的」措辞 | 记忆注入时带了生效日期，它能区分「刚说的」与「以前说的」 |

### 7.2 已知的真实问题（开发过程中实测发现的）

```text
① 记忆重复：同一事实产生两条
   实测：「用户养了一只猫，名叫团子」与「用户养了一只名叫团子的猫」
   原因：无槽位记忆不受 uq_memories_current_slot 约束（C28 的设计），
        其重复只能靠抽取器的语义判重，而那个判重目前不够强。
   影响：Memory Noise 指标偏高。这是**已知设计取舍**，不是 bug。

② 事实时间可能不准
   实测：用户说「我上周三搬到杭州」，事件记为 09-16（正确），
        但记忆的 valid_from 曾写成对话当天 09-23。
   已修（抽取契约增加 validFrom 字段），但模型不一定每次都填。

③ 检索权重只在小语料上校准过
   NORM_VECTOR_MIN=0.35 是在 12–41 条语料上调出来的。
   记忆量显著增长后必须重跑 pnpm eval:retrieval 重新校准。
```

## 8. 接下来最该看的三件事

用一段时间之后，重点观察：

```text
① 该想起来的时候想起来了没有
   问「我之前说过什么关于 X 的事」时，它答得出来吗？
   答不出来 → 检索问题（权重可调，评测集已就绪）

② 记住的东西对不对
   「记忆」页里有没有明显错误或过时的条目？
   特别注意有没有把它的推测记成你的事实 —— 那是最严重的一类错误

③ 有没有变啰嗦或变笨
   记忆多了之后，注入的 8 条里可能混进无关内容，
   反而干扰回答。这是「召回率 vs 噪声」的取舍，需要真实数据才能判断
```
