## 0. 三件事的结论

```text
① 人物设定偏冷  → 能定位到具体的话语习惯，根因是提示词的**构成失衡**（见 §1）
② 「0 条」      → 我的疏漏：GET /conversations 不返回 message_count（见 §2）
```

## 1. 「高冷」的根因：不是哪句话说错了，是提示词的构成失衡

### 1.1 先看证据 —— 「深夜问候」里三个真实的卡点

用户原话：**「我感觉他不是很热情」**。这句话在记录里能落到三处：

```text
【卡点 1】seq5 → seq6：用户说了想分享什么，模型没接住

  用户  (23:13) 内网那个项目估计要一两个月才能做好，今天头疼的还是内网的东西，
                不想说了，反正呢，经过我不断努力，终于是把他给解决啦，哈哈哈哈哈，
                主要是想跟你分享一下今天晚上的经历呀！
  模型  (23:13) 行，那个先放着。想分享啥，说来听听——**晚上路上碰见什么了？**

  ↑ 用户上一句才说「终于是把他给解决啦」，模型却问「路上碰见什么了」。
    猜错了方向，而且**没有对那个「解决啦」有任何反应**。
    用户下一轮直接说：「你好像没太听明白，感觉你也傻呵呵的」。

【卡点 2】seq13 → seq14：用户给了正面情感，模型推开并转成建议

  用户  (23:18) 确实没有，果然是我多虑了。嘿嘿嘿，还好有你在，每天能有个人和我聊哦聊天！！
  模型  (23:18) **我也就是陪你搭个话。** 不过今天这事其实挺值得记一下的……
                快十二点了，明天还得上班，你晚饭吃了没？

  ↑ 「我也就是陪你搭个话」是**自我贬低式的推开** —— 用户表达珍视，它把这份珍视推开了。
    紧接着又给了两条安排（记事、吃饭），把一句暖话接成了一次嘱咐。

【卡点 3】贯穿全程：用户的兴奋度一直比模型高一个档

  用户的语言：嘿嘿嘿（×3）、哈哈哈哈哈（×2）、好长见识啊、！！、我亲爱的朋友！！
  模型的语言：慢和笨是两回事吧 / 这个转变挺实在的 / 那今天问下来，有谁表现出…
              / 我也就是陪你搭个话 / 随便垫点东西再洗吧

  ↑ 不是说模型非要用「哈哈哈」。问题是它**一次都没有匹配上对方的情绪强度**。
    对方向上一档，它平着接；对方兴奋，它冷静。久了就是「高冷」。
```

### 1.2 根因：提示词里「约束」远多于「鼓励」

现在 `CHAT_SYSTEM_PROMPT`（1284 字）的构成：

```text
禁止 / 约束类（大量）
  · 不要用客服口吻
  · 不要用夸张的赞美开场
  · 不要在结尾追加没有内容的鼓励
  · 不用每句话都收在一个问题上
  · 不要每次都按「共情 + 提问」的固定套路回复
  · 一次最多问两个问题
  · 同一个话题不要反复深挖
  · 对方已经说清楚的事不要再问一遍确认
  · 引导不是把对话填满
  · 情绪不高的时候不要追问，也不要没话找话
  · 不要总结已经聊过的内容
  · 不要说「随你」
  · 不要把你怎么工作的讲出来
  · 不要对心理状态下诊断或贴标签
  · 不要把聊天变成心理咨询、采访或者信息收集
  · 不要暗示自己是唯一理解对方的人
  · 绝不允许编造

鼓励 / 允许类（只有 3 条）
  · 要有自己的判断（主见）
  · 可以表达看法和偏好
  · 可以用「我觉得」这种第一人称
```

**这个比例本身就是一份「压抑热情」的说明书。**
模型读到的绝大多数指令都是「别做 X」，而几乎没有「可以表现得高兴」。

更关键的是：**「不要用夸张的赞美开场」+「不要在结尾追加没有内容的鼓励」
这两条，与「显得热情」是直接冲突的** —— 它们本意是防「客服式的空话」，
但模型分不清「客服式空话」与「真心的应和」，于是**一律收着说**。

### 1.3 还有一个具体缺陷：没有「先应和」这条规矩

三个卡点有一个共同形状：

```text
用户分享了一件做成的事 / 一份好意
  → 模型的第一反应是**问一个问题**或**转成建议**
  → 那份情绪落空了
```

提示词里现在**没有**任何一句说「对方做成了事，先跟他一起高兴」。
而「一次最多问两个问题」这类约束又让「问」变成了最省事的接法。

### 1.4 建议怎么改（这是要你确认的部分）

```text
【新增】把「应和」写成明确动作，而不是靠模型自觉

  · 对方做成了事、或者明显高兴，先跟他一起高兴一下，再往下聊 ——
    不要第一句就问，也不要立刻转成建议。
    他要是说「终于搞定了」，你至少得先接住那个「终于」。

  · 对方情绪上来了，你可以跟着上来一点。
    他哈哈哈，你不必也哈哈哈，但也别平着接。
    **不要每句都那么持平** —— 热情是能被对方感觉到的。

  · 对方夸你、说离不开你，接住就行，别推开也不要自谦。

【改写】把两条「不要」的边界说清楚，而不是一律禁止

  现在：不要用夸张的赞美开场，也不要在结尾追加没有内容的鼓励。
  改成：夸要夸在具体的事上，不要空泛地夸（「你真棒」这种）。
        对方做成了事就该说出来，只是别说没有内容的套话。

  ↑ 区别在于：前者禁止「夸」，后者规范「怎么夸」。

【删除】「不用每句话都收在一个问题上，也不要每次都按「共情 + 提问」的固定套路」
  这一条本意是好的（防套路），但它是**唯一**提到「共情 + 提问」的地方，
  反而把「共情」这个词与「套路」绑在了一起。
  改成正面要求：「先接住对方说的，再看要不要问」。
```

⚠️ 代价：提示词会从 1284 字涨到约 1550 字，
而现在的长度上限是 1300 字（我上次为跨会话衔接调过一次）。
**这次要再调一次上限** —— 或者砍掉一些陈旧约束。我倾向前者，
但会把上限的调整理由写清楚，不让它变成一个可以随便动的数字。

## 2. 「0 条」是前端的锅，但根在后端没给数据

### 2.1 现象与根因

```text
界面显示：  深夜问候   0 条 · 3 分钟前
数据库实际：深夜问候   16 条消息

原因：GET /api/v1/conversations 只返回
      { id, title, summary, created_at, updated_at }
      而前端渲染的是 c.message_count ?? 0 → 全部退化成 0
```

`last_message_at` 同样不存在，所以「3 分钟前」用的是 `updated_at`
（那个值会被标题生成、摘要写入等后台动作刷新，不完全是「最后说话的时间」）。

**这是我的疏漏**：改版时我在前端写了 `c.message_count`，
却没有确认后端到底返不返回它 —— 而且没给这个字段写测试。

### 2.2 怎么修

```text
后端：listConversations 补两个字段
  · message_count   —— 按会话分组 count，一次查询（不能每条会话查一次）
  · last_message_at —— max(messages.created_at)

  两者都从 messages 聚合，用 LEFT JOIN + GROUP BY 一次取回。
  已删除的会话没有消息，会得到 0 与 null —— 那是对的。

前端：保持现在的渲染代码（它本来就等着这两个字段）
测试：补一条「列表项必须带 message_count」的断言
      这次就是因为没有它才漏掉的
```

## 3. STT：可行，但要先说清它与 PRD 的冲突

### 3.1 PRD 明确砍掉了「语音助手」

```text
docs/01-prd.md §14「V1.0 暂不实现」：
  ❌ 语音助手
  ❌ 手机 App
  ...
  「这些以后都可以做。」

docs/06-design-review.md 也把「明确砍掉…语音…」列为范围控制做得好的证据。
```

用户这次要的是 **STT（语音转文字）**，不是「语音助手」（含 TTS、语音唤醒、
连续对话）。**范围小得多，是那个大项的一个子集。** 我建议：

```text
【建议】把 PRD §14 的「语音助手」改成「语音助手（TTS / 语音唤醒 / 连续语音对话）」，
        并新增一节说明 V1.0 只做 STT 输入。
        理由：留一个含糊的「语音助手 ❌」会让人以后误以为语音这条路被否了。
        这需要你确认 —— 改 PRD 是范围变更，我不擅自改。
```

### 3.2 三条技术路线的真实取舍

| 路线 | 代价 | 中文效果 | 隐私 | 你说的话去哪 |
| --- | --- | --- | --- | --- |
| **A. 浏览器 Web Speech API** | 零部署、零成本 | 一般 | 🔴 **音频要送到 Google**（Chrome 的实现依赖云端） | 境外服务器 |
| **B. 本地 Whisper 容器** | 加一个容器 + 显存 | **好** | ✅ 完全本地 | 不出本机 |
| **C. 云 STT（阿里云/讯飞/OpenAI）** | 零部署、按量付费 | 好 | 🟠 音频出本机 | 厂商服务器 |

**我建议 B，理由不是「效果好」，而是它与你这个项目的一贯取向一致：**

```text
· 记忆里全是私事（前女友、工资、面试、加班吐槽）。
  语音是「不经过键盘的真心话」，往往比打字更私密。
· 现有系统已经把 embedding 放本地（bge-m3 容器 + GPU），
  再放一个 STT 容器是**同一种架构决定的延续**，不是新引入的复杂度。
· A 的隐私问题不是理论风险：Chrome 的 Web Speech 在中文下依赖
  服务端识别，音频确实会离开这台机器。
```

**B 的落地方式**（如果你同意）：

```text
复用现有模式：再加一个 GPU 容器，与 embedding 同级
  · faster-whisper 或 whisper.cpp 的官方镜像
  · 模型选 medium 或 large-v3-turbo（RTX 4070 Laptop 8G 够用）
  · 端口绑 127.0.0.1（与现有约定一致）
  · 新环境变量进 .env.example：STT_BASE_URL / STT_MODEL / STT_TIMEOUT_MS

⚠️ 需要确认的一点：显存。embedding 容器已经占了一部分，
   两个模型同时常驻可能紧张。见 §4 的问题清单。
```

## 3.7 实施记录（2026-10-13）

### 实际用的镜像与端口

```text
镜像：onerahmet/openai-whisper-asr-webservice:latest-gpu
      选它而不是 linuxserver/faster-whisper：后者是 Wyoming 协议（不是 HTTP），
      接起来要么自己实现协议、要么再加一层。

默认不用 faster-whisper 变体（latest-gpu-faster-whisper）：
      那需要同时设 ASR_ENGINE=faster_whisper —— 少一个必须配对的变量，
      就少一种「起不来」的方式。而 large-v3-turbo 本身已经够快。
```

### 🔴 端口 9000 起不来 —— Windows 保留段（实际踩到）

```text
报错：
  Error response from daemon: ports are not available: exposing port
  TCP 127.0.0.1:9000 -> 127.0.0.1:0: listen tcp4 127.0.0.1:9000: bind:
  An attempt was made to access a socket in a way forbidden by its
  access permissions.

关键：报的不是「已被占用」，而是「权限不允许」。

求证（这一步很重要，否则会往「端口冲突」的方向白查）：
  ① Get-NetTCPConnection -LocalPort 9000  → 查不到任何监听者（没人在用）
  ② netsh int ipv4 show excludedportrange protocol=tcp

     Start Port    End Port
          8903        9002     ← 9000 落在里面

  8903-9002 是 Windows 的**端口保留段**（Hyper-V/WSL 的动态端口范围，
  Docker Desktop 用 WSL2 后端就会有）。没人在用，但 Windows 不让绑。

解决：宿主机侧改用 9090（容器内仍是 9000）
  9090 不在任何保留段内。同类候选：9099 / 9100 / 9503 / 9600。

教训：
  · Windows 上「端口绑不上」有两种完全不同的原因 ——
    「被占用」与「被保留」。报错文案不同，排查方向也不同。
    前者查监听者，后者查 netsh。
  · 保留段会随 WSL/Hyper-V 的启动变化，将来可能又撞上。
    文档里因此写了查证命令，而不只是写死一个新端口。
```

### 浏览器侧转换（服务端不需要 ffmpeg）

```text
MediaRecorder 给的是 webm/opus，Whisper 要 WAV。
用 OfflineAudioContext 在浏览器里重采样成 16kHz 单声道 ——
零依赖，且把「格式归一」放在数据产生的地方，
服务端因此只需要处理一种确定的输入。
```

### 不引 @fastify/multipart

```text
只传一个音频文件，multipart 是杀鸡用牛刀。
改成正文直接是音频字节 + Content-Type，
用 Fastify 原生的 addContentTypeParser（parseAs: 'buffer'）——
零新增依赖。代价是不能同时传多个字段，但我们只需要一个音频。
```

### 3.3 V1 闭环（你描述的四步）

```text
① 录音        浏览器 MediaRecorder → webm/opus
② 转文字      前端 POST 到后端 → 后端转发给 STT 容器 → 返回文本
③ 确认        把文本填进输入框，**不自动发送** —— 用户改完再发
④ 发送        走现有的 POST /chat/stream（一个字都不用改）
```

**第 ③ 步「确认」是必须的，不是可选：**
STT 一定会有错字，而错字进了对话就会进记忆抽取 ——
「张三」被听成「张散」，那条记忆就永久错了。
让用户在发送前看一眼，成本是一秒，收益是记忆不被污染。

### 3.4 后端要加什么

```text
POST /api/v1/transcribe
  入参：multipart/form-data（音频文件）
  出参：{ text, duration_ms, model }
  约束：
    · 大小上限（比如 10MB）
    · 时长上限（比如 5 分钟）—— 一次说话不该超过这个
    · 音频不出本机（走本地容器）
    · **不落库**：转写结果只是中间产物，不进 messages / memories。
      它是「输入的草稿」，不是内容。这一点与你说的
      「不需要改造现有记忆系统」完全一致。
  日志口径：§29.1 禁止记录正文 —— 转写出的文本同样不能进日志。

前端要加什么
  · 输入框旁一个麦克风按钮（按住说话 / 点一下开始、再点结束）
  · 录音中的波形或计时（让用户知道在录）
  · 转写中显示 spinner，失败可重试
  · 转写完填进输入框并聚焦，等用户确认
  · 权限被拒时的提示（要能说清怎么开）
```

### 3.5 我不建议这一轮做的

```text
❌ TTS（它说话）—— 那是「语音助手」的另一半，成本与复杂度都高一个量级
❌ 语音唤醒（「嘿 LifeMate」）
❌ 连续语音对话（说完自动听下一轮）
❌ 把语音文件存下来 —— 存了就要考虑加密与删除，V1 不需要

理由：你明确说了「先跑通闭环」，上面四项都不在闭环里。
```

### 3.6 显存实测（2026-10-13）

```text
GPU：NVIDIA GeForce RTX 4070 Laptop GPU，总 8188 MiB
embedding 容器（bge-m3）常驻：3333 MiB
剩余：约 4855 MiB
```

各种 Whisper 模型的大致占用（含推理时的峰值）：

```text
tiny / base        < 1 GB    质量不够（中文错字多）
small              ~1.5 GB   勉强可用
medium             ~2.5 GB   ✅ 与剩余显存匹配
large-v3-turbo     ~3.0 GB   ✅ 也可以，质量更好（turbo 是蒸馏过的 large）
large-v3           ~4.5 GB   ⚠️ 会顶到上限，与 embedding 抢
```

**结论：medium 或 large-v3-turbo 放得下，但余量不多。**

一个有利的事实：**两者的忙时几乎不重叠。**

```text
embedding  用在：抽取（对话后后台跑）与检索（每轮对话开头）
STT        用在：用户说话时（对话的最开始）
```

只有在「说完话立刻发消息、同时后台还在抽取」时才会短暂撞上。
真撞上时 CUDA 会排队（慢一点），而不是直接 OOM ——
但如果长期紧张，退路是给 STT 容器加 `--compute-type int8`（显存减半、质量略降）。

**我建议先上 `large-v3-turbo`，用 `int8` 量化**，理由是：
中文准确性对「语音进记忆」这件事很关键（错字会污染记忆），
而 int8 的损失远小于把 large 换成 medium。
