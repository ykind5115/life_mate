## 0. 先说三个数据揭示的事实

这三条来自你的真实库（不是假设），它们直接改变优先级：

### ① 你有 **23 条 conflict 记忆**，而前端的「记忆」页看不到它们

```text
记忆状态分布：active=66   conflict=23   superseded=1
```

`view=current`（默认）会过滤掉 conflict，得手动切到「全部」（management）才看得到。
而 AGENTS.md 里列的**未完成项第一条就是「记忆冲突裁决 UI」** ——
23 条待裁决的记忆堆在那里，你既看不到也处理不了。

**这是当前最大的功能缺口，而且已经有真实数据在等它。**

### ② 91 条 assistant 消息带着完整轨迹，但 API 把它们丢了

```text
带 metadata 的 assistant 消息 = 91
```

`toMessageDto` 只返回 `{id, role, content, sequence, created_at}` ——
**metadata 整个被丢掉**。也就是说 09-29 那轮辛苦补的轨迹（注入了哪些记忆、
检索命中几路、耗时、token、工具调用）**前端一条都看不到**，只能进 psql 查。

### ③ goals 和 relationships 都是 0 行，而 relationships 连接口都没有

```text
goals 行数 = 0
relationships 行数 = 0
```

```text
· goals 有 6 个端点，前端也在用 —— 但你没建过目标。
  说明「目标」这个功能对你还不是真需求，或者入口太难用。
· relationships **没有任何 API**（只有一张表）。
  AGENTS.md 也把它列为未完成项。
```

**含义**：relationships 做前端等于从零开始（表 → 服务 → API → UI），
而它没有任何数据支撑「这个功能有用」。**我建议这轮不做。**

## 2. 三个技术决策（需要你先定）

### 决策 A：前端要不要上框架？

| 方案 | 代价 | 收益 |
| --- | --- | --- |
| **A1 继续原生**（现状） | 新增 15 个功能 = 大量手写 DOM + 手写状态同步，容易出「界面与数据不一致」 | 零构建、零依赖、Docker 不用改 |
| **A2 原生 + 自建小渲染层** | 要写约 200 行基础设施 | 声明式渲染 + 统一状态，不引入依赖也不加构建 |
| **A3 Preact + Vite** | 加构建步骤、加依赖、Docker/部署要改、现有 DOM 测试要重写 | 组件化、生态成熟，后续复杂 UI 好写 |
| **A4 Next.js + React + Tailwind** | 同上，且更重 | `docs/02 §6` 写的就是这个（原定方向），但 V1.0 单独起 Node 服务没必要 |

**我的建议：A2。**

```text
理由：
· 页面数量还是少（6 个视图），复杂度主要在「数据 → 视图」的映射，
  而不是在组件复用与交互动画 —— 这正是 A2 能解决的
· 加构建步骤的代价不只是工具链：Docker 镜像、CI、本地启动、
  「零构建就能跑」这个当前很舒服的性质都要重新安排
· Preact 的收益要到「同一个组件在多处复用 + 复杂交互状态」才明显，
  现在还没到
· 但**必须**先把渲染层收拢 —— 否则 A1 会在 15 个功能后变成一堆
  手写 innerHTML 与事件绑定，那时再改代价更大
```

⚠️ 这条我不替你定。如果你希望一步到位上 Preact，现在是最好的时机
（代码量还小），我也可以做 —— 只是要接受构建步骤与测试重写。

### 决策 B：改版到什么程度？

```text
B1 只调样式（换配色、间距、圆角、字体）      —— 1 天量级，但结构问题还在
B2 重做布局与信息架构 + 调样式              —— 这是我建议的
B3 连交互模式一起换（比如改成卡片流 / 时间轴主导）
```

**我建议 B2**：现在的信息架构有几个真问题（见 §4），光调样式解决不了。

### 决策 C：这轮做多少功能？

15 个功能一次做完，风险和「一次改太多无法验证」都很大。
建议按 §5 的优先级分批 —— 但**这一条你说了算**，若你要一次全上，我就全上。

## 4. 现在信息架构的真问题

不只是「不好看」，有三处结构问题：

```text
① 对话页与「记忆/时间线」是割裂的
   你在对话里说了一件事，想确认「它记住了吗」——
   得切到记忆页手动搜。而这两个动作是同一件事的两半。

② 记忆页是一条平铺的长列表，没有层次
   90 条记忆平铺；conflict 混在里面；看不出哪些是同一件事的不同版本。
   而记忆的本质是**有版本的**（Q1：不可变事实 + superseded_by）。

③ 时间线只有「全部」一个视图
   分类只有一个下拉框；没有「按月折叠」（后端已经按月分组了）；
   不能编辑、不能手工补录。
```

## 5. 我建议的做法（分三批）

### 第一批：把「已有数据但看不见」的端上来 —— 最高性价比

```text
· 记忆冲突裁决（23 条在等）         → 独立区块「待裁决」
· 记忆详情抽屉：正文 + 槽位 + 状态流转 + 来源对话（可跳转）
· 设置页补齐 4 个偏好 + 时区
· 会话标题可改
```

这一批**不需要动后端**，且立刻解决你库里的实际积压。

### 第二批：让「对话 ↔ 记忆」连起来

```text
· 消息上的轨迹入口（需后端加 metadata 字段）
  —— 折叠式，默认收起，只给好奇的人看
· 记忆来源 → 点进对话原文并高亮那条消息
· 对话页侧栏显示「本会话产出了哪些记忆」
```

### 第三批：时间线与目标

```text
· 时间线：手工补录、编辑、隐藏、按月折叠
· 目标：详情、编辑、归档/恢复、关联的投影记忆
· 回顾：自定义区间
```

## 6. 视觉方向（需要你给偏好）

我不打算自己拍板视觉风格，但有三个问题必须你回答：

```text
① 基调：偏「安静的记事本」还是「有温度的伙伴」？
   · 记事本 → 中性灰、大量留白、信息密度高、字重轻
   · 伙伴   → 暖色调、圆角多、留白少一点、头像/气泡

② 主题：只做浅色，还是浅色 + 深色都要？
   （深色要额外定义一整套变量，成本约多 30%）

③ 对话页的呈现：气泡，还是不分气泡的连续段落？
   · 气泡 → 一眼分清谁说的，但长回答会显得碎
   · 连续 → 更像读一封信 / 读聊天记录导出，适合长文本
   ⚠️ 你自己的对话里 assistant 经常一次说 200+ 字，
      气泡会把它们切成很高的色块。我倾向「连续段落 + 左侧细线」
```
