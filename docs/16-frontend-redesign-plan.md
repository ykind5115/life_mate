### 8.3 知识图谱：一个必须说清的设计决定

用户要「知识图谱」，但库里的真实情况是：

```text
记忆 90 条、事件 12 条、人际关系 0 条、目标 0 条
```

**如果照「图数据库」的直觉做（万物皆节点、实体之间连边），
画出来会是一堆没有边的孤点** —— 看起来像系统坏了。

因此改成**以用户为圆心的一跳图**：每一类节点都由库里真实存在的数据产生，
没有数据的那一类自然不出现。

实施中发现一个关键问题：**「库里有哪些人」这件事只有记忆知道**。

```text
§22.3 的设计是：记忆用 predicate_key='relationship.person' +
object_value=人名 指向一个人，**不建外键**。
于是 relationships 表是「用户手动补全的关系信息」，
而「实际聊到过谁」要读记忆。

实测：relationships 0 行，而记忆里有 2 个人名（「女朋友」「小换（前女友）」）。
只读关系表的话，图谱上一个人都没有 —— 而用户明明聊过这些人。
```

所以人节点**从记忆派生**，与手工录入的关系合并（手工的优先，信息更全）。
未录入关系的人会标注「来自记忆」，用户能看出还没补过信息。

### 8.4 实施中踩到的坑（都值得记）

```text
🔴 core.js 里写了 TypeScript 语法
   public/*.js 是**无构建步骤**的浏览器模块，`export type Child = …`
   这种写法浏览器直接语法错。改用鸭子类型（typeof child.nodeType）。

🔴 不能用 `instanceof Node` / `instanceof HTMLInputElement`
   Node 环境（DOM 测试）里没有这两个构造器，直接 ReferenceError。
   改成鸭子类型判断 —— 反而更稳，也不依赖任何全局。

🔴 首屏时序：renderConversations 在 loadConversations 之前跑
   boot → onRouteChange → showView('chat') → renderChatView
   → renderConversations，此刻 store 里还是初始值。
   实测报 `Cannot read properties of undefined (reading 'length')`
   → 首屏变成一个「加载失败」框，而数据马上就回来了。
   已给所有 render 的解构加默认值（`const { items = [] } = …`）。

🔴 测试桩不忠实：`el.id` 与 `el.dataset` 没映射成属性
   app.js 的 showView 靠 `el.id === 'view-' + name` 判断谁激活，
   而桩把 id 只存进 attrs Map。于是 `el.id` 永远是 undefined，
   **所有视图都不激活** —— 三个用例失败，而产品代码完全正确。

   教训：**「桩不比真实环境严格」的缺陷最危险** ——
        它在测一个不存在的页面，还会让人去改对的代码。
        补法：setAttribute 存进去的东西必须能以属性形式读出来。

🔴 测试夹具自己不自洽
   「来源显示原话」那条我把 message_chars 写死 24，而正文更长，
   于是夹具造出了「已截断」的显示，断言反过来失败。
   夹具的数字要么算出来，要么与正文严格一致。

🟠 DOM 测试会挂住不返回
   app.js 的 checkHealth 是 `setInterval(checkHealth, 30_000)`，
   用的是**全局**定时器，真的建起来之后 Node 进程不退出
   （实测跑了 300 秒还没结束）。测试里必须替换全局 setInterval。

🟠 PowerShell 里写多行 node -e 会被转义搞坏
   正则与引号会被 PowerShell 先解析一遍，报一堆「缺少表达式」。
   改成写 .ts 探针文件，或用 edit 工具直接改源码 —— 后者更快。
```

### 8.5 明确没做的

```text
❌ 数据导出
   PRD §778 只有一句「用户的数据应该尽量可以导出」，
   docs/04 里**没有任何导出接口定义**，后端也没有实现。
   它属于「要新建的功能」，不是「把没用上的后端搬到前端」。
   因此本轮不做 —— 要做的话是独立一轮。

⚠️ 冲突裁决不是原子的
   后端没有专门的裁决端点，前端用 restore + reject 两个请求完成。
   两步之间失败会留下「一条已恢复、一条未标记」的中间状态，
   但那是**可恢复**的（再裁决一次即可）。
   真正的原子裁决端点属于后端改动，已记在这里备查。

⚠️ 图谱只做到「一跳」
   没有做「记忆 → 记忆」的相似度边：那需要两两算向量相似度
   （90 条 = 4005 次比较），而且「语义相似」不等于「有关系」，
   画出来是一团毛线球。等有真实的实体关系数据再说。
```

## 2. 三个技术决策（需要你先定）

### 决策 A：前端要不要上框架？

| 方案 | 代价 | 收益 |
| --- | --- | --- |
| **A1 继续原生**（现状） | 新增 15 个功能 = 大量手写 DOM + 手写状态同步，容易出「界面与数据不一致」 | 零构建、零依赖、Docker 不用改 |
| **A2 原生 + 自建小渲染层** | 要写约 200 行基础设施 | 声明式渲染 + 统一状态，不引入依赖也不加构建 |
| **A3 Preact + Vite** | 加构建步骤、加依赖、Docker/部署要改、现有 DOM 测试要重写 | 组件化、生态成熟，后续复杂 UI 好写 |
| **A4 Next.js + React + Tailwind** | 同上，且更重 | `docs/02 §6` 写的就是这个（原定方向），但 V1.0 单独起 Node 服务没必要 |

**我的建议：A2。**

```text
理由：
· 页面数量还是少（6 个视图），复杂度主要在「数据 → 视图」的映射，
  而不是在组件复用与交互动画 —— 这正是 A2 能解决的
· 加构建步骤的代价不只是工具链：Docker 镜像、CI、本地启动、
  「零构建就能跑」这个当前很舒服的性质都要重新安排
· Preact 的收益要到「同一个组件在多处复用 + 复杂交互状态」才明显，
  现在还没到
· 但**必须**先把渲染层收拢 —— 否则 A1 会在 15 个功能后变成一堆
  手写 innerHTML 与事件绑定，那时再改代价更大
```

⚠️ 这条我不替你定。如果你希望一步到位上 Preact，现在是最好的时机
（代码量还小），我也可以做 —— 只是要接受构建步骤与测试重写。

### 决策 B：改版到什么程度？

```text
B1 只调样式（换配色、间距、圆角、字体）      —— 1 天量级，但结构问题还在
B2 重做布局与信息架构 + 调样式              —— 这是我建议的
B3 连交互模式一起换（比如改成卡片流 / 时间轴主导）
```

**我建议 B2**：现在的信息架构有几个真问题（见 §4），光调样式解决不了。

### 决策 C：这轮做多少功能？

15 个功能一次做完，风险和「一次改太多无法验证」都很大。
建议按 §5 的优先级分批 —— 但**这一条你说了算**，若你要一次全上，我就全上。

## 4. 现在信息架构的真问题

不只是「不好看」，有三处结构问题：

```text
① 对话页与「记忆/时间线」是割裂的
   你在对话里说了一件事，想确认「它记住了吗」——
   得切到记忆页手动搜。而这两个动作是同一件事的两半。

② 记忆页是一条平铺的长列表，没有层次
   90 条记忆平铺；conflict 混在里面；看不出哪些是同一件事的不同版本。
   而记忆的本质是**有版本的**（Q1：不可变事实 + superseded_by）。

③ 时间线只有「全部」一个视图
   分类只有一个下拉框；没有「按月折叠」（后端已经按月分组了）；
   不能编辑、不能手工补录。
```

## 5. 我建议的做法（分三批）

### 第一批：把「已有数据但看不见」的端上来 —— 最高性价比

```text
· 记忆冲突裁决（23 条在等）         → 独立区块「待裁决」
· 记忆详情抽屉：正文 + 槽位 + 状态流转 + 来源对话（可跳转）
· 设置页补齐 4 个偏好 + 时区
· 会话标题可改
```

这一批**不需要动后端**，且立刻解决你库里的实际积压。

### 第二批：让「对话 ↔ 记忆」连起来

```text
· 消息上的轨迹入口（需后端加 metadata 字段）
  —— 折叠式，默认收起，只给好奇的人看
· 记忆来源 → 点进对话原文并高亮那条消息
· 对话页侧栏显示「本会话产出了哪些记忆」
```

### 第三批：时间线与目标

```text
· 时间线：手工补录、编辑、隐藏、按月折叠
· 目标：详情、编辑、归档/恢复、关联的投影记忆
· 回顾：自定义区间
```

   · 伙伴   → 暖色调、圆角多、留白少一点、头像/气泡

② 主题：只做浅色，还是浅色 + 深色都要？
   （深色要额外定义一整套变量，成本约多 30%）

③ 对话页的呈现：气泡，还是不分气泡的连续段落？
   · 气泡 → 一眼分清谁说的，但长回答会显得碎
   · 连续 → 更像读一封信 / 读聊天记录导出，适合长文本
   ⚠️ 你自己的对话里 assistant 经常一次说 200+ 字，
      气泡会把它们切成很高的色块。我倾向「连续段落 + 左侧细线」
