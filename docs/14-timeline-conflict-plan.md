# Timeline 冲突问题分析与方案

**日期：** 2026-09-29
**来源：** 用户实测发现 —— 时间线上有两条互相冲突的记录
**状态：** ✅ **已实施** —— 用户的决定是「不做覆盖，只修时间」

---

## 0. 用户的决定（2026-09-29）

```text
「这个没必要做覆盖，只是同一件事情在不同的时间点做出了不同的决定，
  不能算作是冲突。但是那个展示出来的时间是要记录事件发生的时间」
```

**这个判断是对的**，而且它把方案收窄了很多：

```text
❶ 不做事件替代（原方案 B）—— 两次不同时间的决定都是真实发生过的，
   没有谁「替代」谁。删掉或标记任何一条都是在抹掉真实历史。

❷ 要修的是「事件时间」—— 两条记录的 event_time 都落在 08:00，
   而它们其实是不同时刻发生的。这个 08:00 是**编造出来的**。
```

因此本次**只做原方案 A**，方案 B（替代语义）与 C（界面提示）都不做。
理由留在 §3，以备将来重新讨论。

## 0. 先说结论：系统没有记错，是**呈现**出了问题

用户给的两条：

```text
2026-09-29  work  确定录用的候选人
  用户当天上午面试了候选人，中午与领导商量后最终确定录用上午面试的第二位候选人，
  其余候选人不予考虑。

2026-09-28  work  团队确定录用前一日面试的候选人
  用户所在团队由领导拍板，确定录用前一天面试的那位候选人，
  用户当天上午还有两场面试要参加，但认为只是走过场。
```

**这两条都不是编的 —— 它们各自忠实复述了用户当时真实说过的话。**
我把两次对话的原文找出来了：

```text
【09-29 上午 09:30】用户说：
  「对呀，今天上午还有两个面试呢，先看看吧，这边领导已经定了就昨天那个人，
   所以今天这两个估计就是走个过场」
  ↓ 抽取为「团队确定录用前一日面试的候选人」，事件时间 = 09-28（昨天）

【09-29 下午 13:57】用户说：
  「问了呀，我说可以的……」
  （模型回答确认：「上午第二位是你自己面出来说能力强的」「等着入职吧」）
  ↓ 抽取为「确定录用的候选人」，事件时间 = 09-29（今天）
```

所以系统记录的是**两次真实陈述**。冲突感来自两处，都不是「记错」：

| # | 问题 | 性质 |
| --- | --- | --- |
| **①** | 两条并列显示，**没有标明时间先后**。用户看到的是「同一天（9月28日）确定录用 A」和「9月29日确定录用 B」，像是同一天内反复改口 | 🔴 呈现缺陷 |
| **②** | 所有事件的时间都落在 **08:00**，看起来像是同一时刻发生的 | 🔴 数据缺陷 |
| **③** | 「9月28日确定了人选」这条**系统其实是在 9月29日 09:30 才被告知的** —— 库里 `created_at` 有这个信息，但界面上看不到 | 🟠 设计取舍 |

## 4. 实施记录（2026-09-29）

### 4.1 做了什么

```text
① events 新增 event_precision（day | minute），迁移 0005
   · 日期级事件的 event_time 落在**用户当地零点**，而不是 UTC 零点
   · 迁移把已有 11 行从 UTC 零点平移到当地零点（−8 小时）

② 解析层（resolveEventTime）按精度解析
   · 落在 UTC 零点上的输入 → day（模型常照旧示例写 T00:00:00Z）
   · 中文「2026年9月29日 15:00」→ minute，且按**用户当地**时刻解释
     （不带偏移解析会让北京的下午三点变成当地晚上十一点）

③ 合理性判据收敛为 gate()，所有分支共用
   此前只有 ISO 分支检查年份，`1899-12-31` 走「只有日期」分支会被放行

④ 抽取提示词
   · 明确「eventTime 是**事件发生的时间**，不是用户告诉你的时间」
   · 补上精度分档：知道时刻就写时刻，只知道日期就写日期，
     **不要输出 T00:00:00 来表示「只知道日期」**
   · 「当前时间」从「UTC 日期」改成「用户当地的日期 + 时刻 + 时区名」

⑤ 修掉一个**系统性**的时区缺陷（9 处 toISOString().slice(0,10)）
   新增 shared/local-time.ts 统一处理，并加了 12 条单测钉住它

⑥ 时间线按月分组、日期边界查询也改用用户时区
```

### 4.2 实测结果

```text
【修复前】所有事件都显示成 08:00
  2026-09-29 08:00  确定录用的候选人
  2026-09-28 08:00  团队确定录用前一日面试的候选人

【修复后】日期级事件落在当地零点，界面只显示日期
  2026-09-29  确定录用的候选人
  2026-09-28  团队确定录用前一日面试的候选人
  （界面不再显示 00:00 —— 精度是 day 就不渲染时刻）

【顺带修正的日期】
  「开始出来工作」2026-05-01 → 原本 UTC 口径算成 04-30（北京 5月1日零点 = UTC 4月30日16点）
```

重新跑抽取评测（docs/09 基线 P=0.900 R=0.818 F1=0.857）：

```text
① Memory Precision   100.0%   （基线 90.0%）
② Memory Recall       90.9%   （基线 81.8%）
  F1                  95.2%   （基线 85.7%）
③ Memory Noise         0 条   （基线 0 条）
  槽位正确率           85.7%   （基线 83%）
  类型正确率           70.0%   （基线 67%）
```

⚠️ **不要把这组数字当成「提示词改动让质量变好了」**：
抽取评测不是确定性评测（每组对话调一次 LLM），单次运行的波动本来就在这个量级。
能确认的只有一件事：**没有变差**。这也正是本次改提示词的目的 ——
改的是时间语义，不该影响记忆抽取质量。

### 4.3 过程中犯的错（留档）

```text
🔴 迁移方向写反了
   第一版写成 `event_time + INTERVAL '8 hours'`，
   而正确方向是**减** 8 小时。加 8 小时得到 UTC 08:00（= 北京 16:00），
   离目标多出 16 小时 —— 差点静默改坏用户的时间线。

   发现方式：核对「北京墙上时间是否正好是 00:00」，而不是只看
   「脚本跑成功、UPDATE 11」。
   已用 audit/fix-0005-event-time-shift.sql 订正。

   教训：**改时间数据的迁移必须断言换算后的墙上时间。**
        行数正确、SQL 无错、退出码 0 —— 这些都说明不了方向对不对。

🔴 迁移文件在已应用之后被修改
   表结构部分（加列 + 约束）是对的，数据订正部分是错的。
   表结构对而数据错时，追加新迁移会让新库多跑一次错误的订正。
   因此修改了它，并在文件头记下这是**有意识的例外**
   （尚未发布、机器只有本机、drizzle 只记 tag 不比对内容）。
   这不应成为先例：正常做法是追加新 migration。

🟠 测试断言写错，先怀疑了代码
   `1970-01-01T00:00:01Z` 期望被拒 —— 但判据本来就是「早于 1900」，
   1970 合法。断言错了，代码没错。
   后来又踩到一个真的边界：`1900-01-01` 在北京是 `1899-12-31T16:00Z`，
   用 UTC 年份判断会误拒 —— 判据改成按**用户时区**的年份。

🟠 评测脚本的 cleanup 有缺陷（顺手修了）
   它漏删 events / goals / relationships / extraction_runs，
   而它们对 users 都是 RESTRICT 外键 —— 于是 `delete from users` 失败，
   评测跑完却留下一整个用户与它的数据，
   而且报错显示成「评测失败」（其实指标已经算完）。
```

### 4.4 没做（用户的决定）

```text
❌ 事件替代语义（status + superseded_by）
   用户判断：两次不同时间的决定都是真实发生过的，不构成冲突，
   没有谁替代谁。给事件加替代会抹掉真实历史。

❌ 界面上的「冲突提示」
   同上的理由 —— 既然不是冲突，就不需要提示。

❌ 界面显示「你什么时候提到的」
   原先是为「让用户看出两条的先后」准备的。既然不做冲突处理，
   这个需求也跟着弱了。若将来觉得有用，数据已在库里（created_at）。
```

## 5. 核实过的事实（可复现）

### 1.1 `created_at` 揭示了真相

```text
title                          | 事件时间 | 系统得知于
-------------------------------+---------+---------------
开始出来工作                    | 05-01   | 09-24 10:25
接手 AI 问卷流程项目            | 09-28   | 09-28 09:57
第一次担任面试官                | 09-28   | 09-28 16:33
团队确定录用前一日面试的候选人   | 09-28   | 09-29 09:30   ← 晚了 1 天
确定录用的候选人                | 09-29   | 09-29 13:57
```

**「9月28日确定录用 A」这条，系统是在 9月29日 09:30 才知道的。**
而「9月29日确定录用 B（上午第二位）」是 13:57 知道的。

两次陈述相隔 **4.5 小时**，说的是**同一件事在新信息下的修订**。
双时间轴（事实时间 / 记录时间）本来就是为了表达这个 —— 数据没丢，
只是界面没展示。

### 1.2 为什么都落在 08:00

```text
模型输出   "2026-09-29T00:00:00Z"     ← 提示词示例用的就是 UTC 零点
解析       resolveEventTime() 对「只有日期」按 UTC 零点解析
落库       2026-09-29 00:00:00+00
界面显示   08:00（北京 = UTC+8）
```

08:00 是个**伪时刻**：它不代表「上午八点发生」，只代表「这一天，具体时刻未知」。
但界面上它和真实时刻长得一模一样。

顺带说明：提示词里确实写了「只知道年月、不知道具体哪天 → 用该月 1 号，
不要编造具体日期」—— 方向是对的（不编造），但**没有覆盖「日期知道、
时刻不知道」这一档**，也**没有要求给出能确定的更细时间**。

### 1.3 事件的去重规则帮不上忙

`event-writer.ts` 的去重判据是**「同一 UTC 日期 + 标题完全一致」**：

```text
「团队确定录用前一日面试的候选人」 vs 「确定录用的候选人」
  → 标题不同，判不出来
```

而事件**没有任何替代（supersede）机制** —— 记忆有 `status` +
`superseded_by`，事件一个字段都没有。写进去就永远并列。

## 2. 问题拆解

把「冲突」拆开，其实是五件独立的事。分开看才知道各自该不该修：

```text
P1  时间精度丢失      日期级事件被表示成 08:00，且无法区分
                      「这一刻发生的」与「只知道是这天」

P2  日期串了时区      resolveEventTime 把「YYYY-MM-DD」按 UTC 零点解析，
                      而按用户时区（UTC+8）应该是当地零点。
                      当前恰好因为事件都是 00:00Z 才在显示上不出错 ——
                      一旦有了带时刻的事件，就会出现「差一天」

P3  无替代语义        事件写进去就并列，没有「后被修正」的表达

P4  界面不显示记录时间 用户看不到「这条是什么时候告诉系统的」

P5  无冲突提示        就算保留两条，也没告诉用户「这两条可能相关」
```

**P2 值得单独说**：它现在是个**潜伏的 bug**。看这段代码：

```js
// public/app.js 渲染事件日期
e.event_time.slice(0, 10)
// src/memory/tools.ts 给模型看的时间
e.eventTime.toISOString().slice(0, 10)
```

`toISOString()` 返回的是 **UTC** 日期。北京用户晚上 10 点发生的事，
存进去是 UTC 次日 14:00，`slice(0,10)` 会显示成**第二天**。

现在看不出来，是因为所有事件都是 `00:00Z`（= 当地 08:00，同一天）。
**等 P1 修好、事件带上真实时刻，这个 bug 立刻会暴露。**

## 3. 方案

### 方案 A：显式的时间精度 + 修掉时区 bug

**做什么**

```text
① events 新增 event_precision 列（day | minute | approx）
   迁移：已有行全部回填 'day' —— 它们本来就是日期级

② 解析层按精度落库
   · 模型给了日期 + 时刻 → 精度 minute
   · 只给到日期         → 按【用户时区】的当地零点落库，精度 day
   这样「9月29日发生的事」在任何显示时区下都还是 9月29日

③ 提示词补一档
   现在：「只有年月不知道哪天 → 用该月 1 号」
   补上：「知道日期、也知道大概时刻 → 写出来（如 2026-09-29T13:00:00+08:00）；
         只知道日期 → 写日期；不要为了显得精确而编造时刻」

④ 显示层：精度为 day 的不显示时刻，只显示「9月29日」；
   界面与工具统一用【本地时区】取日期，不再 slice(0,10)
```

**收益**

```text
✅ 「都落在 08:00」消失：日期级事件不再伪装成某个时刻
✅ 消除 P2 那个潜伏的差一天 bug
✅ 精度可查询：将来可以统计「多少事件的时刻是编的」
```

**代价与风险**

```text
· 一次迁移（加列 + 回填），成本低 —— 与 C39 同量级
· 改提示词 → 要重跑抽取评测对齐基线（docs/09）
· 「不要编造时刻」这条约束可能让模型过度保守、少给时刻。
  需要在评测里看「minute 精度的占比」，太低说明约束给重了
```

**这一条我建议先做**：它是其余方案的地基 —— 没有真实时刻，
「同一天内的先后顺序」根本无从谈起。

---

### 方案 B：事件也支持「被替代」

**做什么**

```text
① events 新增 status（active | superseded）+ superseded_by
   完全照 memories 的成熟做法（含 C23 的教训：superseded_by 不加外键，
   否则物理删除会被阻塞）

② 抽取器在「用户报告同一件事的新进展」时，把旧事件标记为 superseded
   判据（三者同时满足才动）：
     · 同一 category
     · 事件时间相近（比如 7 天内）
     · 模型判断「后一条是前一条的更新」
   → 交 LLM 判定，且**默认不动**（宁可漏判，不可错判）

③ 界面：被替代的事件折叠显示，或标注「已更新为 …」
```

**收益**

```text
✅ 用户看到的是「当前状态」而不是一堆并列的历史陈述
   —— 人的心智模型本来就是「现在是什么样」，
      不是「先后有过哪些说法」
✅ 保留完整历史（这一点比删除好得多）
```

**代价与风险（这是我最犹豫的一条）**

```text
🔴 判据本身要引入 LLM 调用，而**判错的代价比漏判大**：
   把两件不相干的事标成「B 替代了 A」= 在时间线上抹掉一个真实事件，
   比多留一条并列记录糟糕得多

🔴 它和 Q1（记忆不可变 + superseded_by）的关系要说清楚：
   事件没有槽位、没有唯一键，「同一件事」的判定比记忆难得多。
   记忆靠 slot 可以确定性判定，事件只能靠语义
```

**我的倾向**：**先只加字段，先不启用自动判定。**

理由：数据模型现在改便宜（一条迁移），而判定逻辑应该等
方案 A 落地、有了真实时刻之后再设计 —— 到那时「事件时间相近」
这个判据才有意义（现在所有事件都在 08:00，「相近」无从判断）。

启用的第一步可以更保守：**只在用户明确说「改主意了 / 不是那个了」
这类修正语气时**才标记，而不是让模型自由判断相似性。

---

### 方案 C：界面显示「系统何时得知」+ 冲突提示

**做什么**

```text
① 事件卡片上加一行小字：「你 9月29日 09:30 提到」
   —— 数据已在库里（created_at），不需要改 Schema

② 同一 category 且事件时间相近的相邻事件，界面加一个轻提示
   「这两条看起来是同一件事？」并提供「合并 / 标记为替代」的手动操作
```

**收益**

```text
✅ 不改 Schema、不加 LLM 调用，成本最低
✅ 立刻消解用户这次遇到的困惑：
   看到「你 9月29日 09:30 提到」+「你 9月29日 13:57 提到」，
   一眼就明白后者是对前者的修订
✅ 把「该不该合并」的决定权交给用户，而不是让模型猜
```

**代价与风险**

```text
· 手动操作需要用户动手（但这类冲突本来就不多）
· 界面上多一行字，密集时间线会变吵 → 可以做成 hover 才显示
```

## 4. 我建议的顺序

```text
第 1 步（低风险、立刻见效）
  方案 A：时间精度 + 时区 bug + 提示词补一档
  → 解决「都落在 08:00」，并消除那个潜伏的差一天 bug

第 2 步（零 Schema 改动）
  方案 C①：界面显示「你 X 月 X 日提到」
  → 用现有数据消解这次的困惑。做完这两步，
    你这次遇到的那两条会显示成：
      「9月29日 你 09:30 提到：团队确定录用前一日面试的候选人」
      「9月29日 你 13:57 提到：确定录用的候选人」
    先后关系一目了然，不再像矛盾

第 3 步（数据模型先备好，判定先不启用）
  方案 B 的 ①：加 status + superseded_by 两个字段
  → 迁移便宜，先备着；判定逻辑等第 1 步的真实时刻落地后再设计

第 4 步（要你先定）
  方案 B 的 ②：抽取器自动标记替代
  → 我倾向只处理「用户明确改口」这一种情形，且默认不动。
    要不要做、做到什么程度，需要你定

暂不做
  方案 C② 的自动冲突提示（需要相似度判断，等有频率数据再说）
```

## 6. 一个额外发现（与本问题无关，但顺手记下）

`src/memory/tools.ts` 给 Agent 看的时间也是 `toISOString().slice(0, 10)`：

```text
get_timeline 返回给模型的事件日期是 UTC 日期。
用户在北京，晚上发生的事会被模型看成第二天 ——
而 Agent 用这个日期回答「你什么时候面试的」，就会答错一天。
```

它与 P2 是同一个根因（用 UTC 日期当本地日期），修的时候一起处理。
