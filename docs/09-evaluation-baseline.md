# 离线评测基线记录

> 目的：记住「改动前是多少」，否则调优方向全靠感觉。
>
> 每次改提示词 / 词表 / 抽取模型后跑 `pnpm eval:extraction` 并**追加一行**到下面的表。
> 不要在原地改历史数据 —— 基线一旦被覆盖就失去了对比意义。

---

## 怎么跑

```powershell
# 方式一：临时覆盖库地址（推荐，不需要新建文件）
$env:DATABASE_URL="postgresql://lifemate:<密码>@127.0.0.1:5432/lifemate_test"
pnpm eval:extraction

# 方式二：复制 .env.eval.example 为 .env.eval 并填真实 key
pnpm eval:extraction

# 前置：postgres 与 embedding 容器在跑
docker compose up -d postgres embedding
```

⚠️ 评测会**真实调用 LLM**（每组对话 2 次：抽取 + 评审）。
5 组对话约 20~25 秒、10 次调用。改提示词时注意成本。

⚠️ 评测会**写库**。脚本默认拒绝在非测试库上运行；
确需在开发库上跑要显式设 `ALLOW_EVAL_ON_DEV_DB=1`（会新增数据，结束后自动清理）。

## 指标定义

PRD §15 只给了问题，没有给公式。以下是本实现采用的可计算定义：

```text
recall    = 被覆盖的期望数 / 期望总数
            分子分母都在「期望」一侧，因此与模型是否合并/拆分无关。

precision = 有用抽取数 / 抽取总数
            「有用」= 这条抽取被用来覆盖了至少一条期望。
            未被任何期望引用的抽取算多余（含噪声）。

noise     = 命中 shouldNotExtract 的条数（绝对值）
            单独计数而不是并入 precision：
            抽出一条"无害但没用"的记忆，与把助手的推测记成用户事实，
            严重性完全不同 —— 后者会污染后续所有对话。混在一起会掩盖后者。
```

**已知口径偏差（都是保守方向，即指标偏低而非偏高）：**

```text
• 评审用「逐条期望问是否被覆盖」而不是 1:1 匹配。
  好处：模型合并多条信息时不扣 recall（实测踩到过 1:1 的误判）。
  代价：评审可能漏填 byActualIndexes，使 precision 偏低。

• 提示词要求「宁可漏记不可错记」，因此 recall 天然不会很高。
  这不是缺陷，是产品取向（PRD §10.2 + 抽取提示词的判断标准）。
```

## 基线记录

| 日期 | 抽取模型 | 提示词版本 | P | R | F1 | noise | slot | type | 备注 |
| ---- | -------- | ---------- | - | - | -- | ----- | ---- | ---- | ---- |
| 2026-09-23 | deepseek-flash | v1 | 0.900 | 0.818 | 0.857 | 0 | 0.83 | 0.67 | 首版基线。10 条抽取 / 11 条期望 |

**首版基线的原始输出：**

```text
  ① Memory Precision   90.0%
  ② Memory Recall      81.8%
     F1                85.7%
  ③ Memory Noise       0 条（噪声率 0.0%）
     槽位正确率         83.3%
     类型正确率         66.7%
  合计：抽取 10 条，期望 11 条
```

### 首版基线暴露的问题（按值得修的顺序）

```text
① 类型正确率 66.7% —— 最弱的一项，也是最值得查的。
   模型在 fact / preference / state 之间摇摆。
   提示词里对三者的边界只有一行说明，可能不够。

② 信息拆分粒度不稳定：同一段信息这次合成一条、下次拆成两条，
   有时还会把「居住」与「工作」都塞进同一条并标 residence.city。
   影响：槽位正确率与类型正确率都会被它带偏。
   注意这不影响 recall（覆盖口径已屏蔽），但会影响可读性。

③ 评审对"额外断言"偏严格：
   「攒够首付、购买一套小两居」被标为无依据，而用户其实说了「买个小两居」。
   这是评审的问题不是模型的问题 —— 但它只影响 ungrounded 记录，
   不影响 precision（默认宽松口径）。
```

### 下一步的用法

上表是**起点**。任何提示词改动后：

```text
1. 跑评测，记录新一行
2. 与本行对比：三项主指标里哪项动了、动多少
3. 若某项下降，先确认是不是口径问题（看 notes 里的输出），再决定要不要回退
4. 指标改善但人看输出觉得更差的 → 以人看为准，并**同时**改标注或指标定义
   （说明当前指标没有抓住你真正在意的东西）
```

## 待补：检索质量评测

### 检索质量（PRD §15 ② Memory Recall）—— 已建立

```powershell
# 需要 postgres + embedding 容器；不调用 LLM（检索本身不用模型）
$env:DATABASE_URL="postgresql://lifemate:<密码>@127.0.0.1:5432/lifemate_test"
pnpm eval:retrieval
```

评测集是**人工构造的固定语料**（41 条记忆 + 16 个查询），不是真实库。
理由：可复现、可控规模、且刻意包含**主题相关但事实不同**的干扰项 ——
否则「全召回」也能拿满分，测不出区分能力。

| 日期 | R@1 | R@3 | R@8 | MRR | 干扰误召 | 关键词有效查询 |
| ---- | --- | --- | --- | --- | -------- | -------------- |
| 2026-09-23 初版 | 0.625 | 0.646 | 0.938 | 0.712 | 7 | 2/16 |
| 2026-09-23 校准后 | 0.750 | 0.865 | 1.000 | 0.854 | 11 | 11/16 |

**R@8 是最重要的指标** —— 8 是 §18.5 的注入条数，
也就是「实际会影响回答」的那批。当前 100%。

### 评测驱动的两个修正（都是实测发现的真问题）

```text
① 关键词通道对中文几乎完全失效
   · C16 声称 pg_trgm「按字符三元组匹配，适合中文」—— 错。
     show_trgm('用户住在杭州') 返回 {}（实测），CJK 完全不产生三元组。
   · 改用应用层 bigram 后，纯命中率仍不可用：
     查询「我现在住在哪个城市？」8 个 bigram 里 7 个是虚词，
     唯一的内容词「住在」只占 1/8 = 0.13，过不了 0.3 阈值。
     实测 16 个查询只有 2 个有命中。
   · 最终改为 **IDF 加权**：虚词权重趋近 0，内容词单命中即可入选。
     → 关键词有效查询 2/16 → 11/16。

② NORM_VECTOR_MIN = 0.5 是错的（我估的值）
   · 实测向量相似度分布：max 0.641 / p50 0.446 / min 0.303，
     **只有 12.5% 超过 0.5** → 占权重 0.55 的向量项对绝大多数候选归零
     → 排序实际由 importance 与 recency 决定（MRR 卡在 0.712）。
   · 观测：相关查询 top1 = 0.539~0.641；无关查询 top1 = 0.363~0.402。
   · 校准为 0.35（略低于无关上界）→ RR@8 0.938 → 1.000，MRR 0.712 → 0.854。

⚠️ 0.35 只在 12~41 条语料上校准过。**语料规模会影响该值**
   （语料越大，无关内容的相似度通常越低）。
   记忆量显著增长后必须重跑评测重新校准 ——
   评测集里刻意放「量子力学」这类无关查询就是为了这个。
```

### 已知的评测集局限

```text
· 干扰项误召从 7 升到 11 —— 因为召回总量上升，被带出来的干扰项也多了。
  但 R@8 已 100%，且干扰项都是「主题相关」而非有害内容，
  在注入条数内不影响正确性。若将来要收紧，需引入相关性下限，
  而那需要更多标注才能校准（当前样本量不够）。
· 语料是构造的，不反映真实使用的查询分布。
· 未评测「跨会话的长期一致性」（PRD §15 ⑤）—— 那需要数月的真实数据。
```

## 其余未覆盖的指标

```text
④ Memory Conflict     部分由单元测试覆盖（candidate-processor.test.ts）
                      测的是判定逻辑，不是端到端的冲突识别质量。
                      端到端需要「同一槽位取值变化」的多轮对话标注。

⑤ Long-term Consistency
                      需要跨会话、跨时间的对话序列，本质上是
                      「用几个月后是否更懂用户」，离线评测很难覆盖，
                      可能要靠实际使用 + 定期人工复核。
```
